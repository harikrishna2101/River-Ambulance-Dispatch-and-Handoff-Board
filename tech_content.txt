1. Product and Technical Goals
The system is an emergency dispatch board for five boat ambulances serving small river islands. The prototype must let a health worker submit an emergency request in seconds, let a captain claim it without double-booking, and let the next shift see fuel and oxygen status immediately.
Primary success criteria
Emergency request can be logged in under 30 seconds on a phone.
Captain can see open requests sorted by urgency and claim a job in one clear action.
Two captains cannot successfully claim the same request.
Boat board exposes availability, fuel percentage, oxygen tank count, and current dispatch state at a glance.
Historical dispatch can be filtered by island without a complex reporting page.
Core UI remains functional on a slow mobile connection and small screen.

The browser reads the operational board directly from Supabase through the official JavaScript client. Mutations that require business rules should use Postgres RPC functions rather than trusting client-side checks. Realtime subscriptions refresh the boat board and dispatch list when rows change.

4. Why This Stack Fits the Challenge
4.1 Speed and simplicity
The operational UI is essentially a structured CRUD workflow with realtime status. A separate REST backend would add another deployment and another failure point without materially improving the prototype. Supabase lets the application keep the database transaction boundary close to the core dispatch rules.
4.2 Free public deployment path
As of 17 September 2026, Supabase lists a $0 Free plan with Postgres, 500 MB database size, 1 GB file storage, and Postgres Changes Realtime with 2 million messages/month and 200 peak concurrent connections. Cloudflare Pages documents a Free plan with static asset delivery free and unlimited, up to 500 builds/month and up to 20,000 files per site. These limits are far above what this five-boat prototype needs. 
Important deployment note: the prototype should remain small enough that it does not depend on paid add-ons, custom domains, large file uploads, or heavy server-side functions. Supabase projects on the Free plan can pause after inactivity, so the demo should be opened and tested before submission. 
4.3 Low-bandwidth behavior
No large hero images, video, maps, or decorative animations.
Prefer system fonts and SVG/Lucide icons; avoid downloading icon font packs.
Load current board data with one compact query per screen; do not refetch unchanged rows every few seconds.
Use realtime events to invalidate/update only affected records.
Cache the application shell and last-known board state in IndexedDB.

7. Critical Workflow: Emergency Request
Health worker opens the Dispatch Request screen.
Selects island and enters pickup location; urgency and patient condition are required.
Client performs lightweight validation, then inserts the dispatch as OPEN.
Realtime event updates all connected captain boards.
The new request appears sorted by urgency, then created_at ascending.
Health worker sees a compact confirmation with the request ID.
Critical Workflow: Captain Claim
Captain opens the queue and taps Claim.
Client calls Postgres RPC claim_dispatch(dispatch_id, captain_id).
Database transaction checks that the dispatch is still OPEN and assigns the selected boat/captain.
If another captain won the race, the RPC returns a conflict status; the UI shows “Already claimed” and refreshes the row.
Successful claim changes dispatch to CLAIMED and boat status to ON_MISSION in the same transaction.
Realtime events update the board for every connected user.
Critical Workflow: Completion
Assigned captain opens Active Mission and presses Complete.
RPC validates that the dispatch is CLAIMED and assigned to the same captain/demo identity.
Dispatch becomes COMPLETED; completed_at is recorded; boat returns to AVAILABLE.
Audit event is appended and the board updates in realtime.

9. Atomic Claim Function (Core Reliability Rule)
This function is the most important piece of backend logic. The UI must never rely on “check status, then update” as two independent requests because that creates a race condition.
-- Conceptual SQL / PLpgSQLBEGIN  UPDATE dispatches     SET status = 'CLAIMED',         boat_id = p_boat_id,         claimed_by = p_captain_id,         claimed_at = now()   WHERE id = p_dispatch_id     AND status = 'OPEN'     AND EXISTS (       SELECT 1 FROM boats       WHERE id = p_boat_id         AND status = 'AVAILABLE'     );  -- If zero rows changed, return a conflict.  -- If one row changed, set the boat to ON_MISSION  -- and write an audit event in the same transaction.END;
For this challenge, the exact SQL can be implemented as a Supabase Postgres function. The important invariant is that dispatch status, boat status, and audit logging are committed together.

Transient UI state: React state for forms, dialogs, filters and loading indicators.
Local persistence: IndexedDB stores the last successful board snapshot and static reference data.

11. Realtime Strategy
Subscribe only to the tables needed for the current screen. For example, the Live Board listens to boats and dispatches; the Handoff screen mainly needs the selected boat. Realtime events should trigger targeted cache updates rather than full-page reloads.
supabase  .channel('operations-board')  .on('postgres_changes', { event: '*', schema: 'public', table: 'boats' }, onBoatChange)  .on('postgres_changes', { event: '*', schema: 'public', table: 'dispatches' }, onDispatchChange)  .subscribe()
Supabase documents Postgres Changes as a realtime mechanism for listening to inserts, updates and deletes. Its current Free plan lists 2 million Realtime messages per month and 200 peak concurrent connections.

13. Security and Access Model
The challenge explicitly avoids a complex login flow, so the prototype should use a lightweight demo identity model while still demonstrating correct database authorization boundaries.
Recommended prototype model
On first load, present a “Continue as Health Worker” / “Continue as Captain” role selector.
Generate a temporary anonymous Supabase identity or lightweight session token.
Store the selected display role in session state; never store secrets in localStorage.
Use RLS policies to protect tables from unrestricted direct access where practical.
Keep privileged state changes inside RPC functions so the client cannot arbitrarily set CLAIMED/COMPLETED status.
For a real clinical deployment, this demo access model would not be sufficient. Production would require stronger identity verification, least-privilege roles, audit retention, privacy controls, and formal operational/security review. Those are deliberately outside the hackathon prototype scope.
