PRODUCT REQUIREMENTS DOCUMENT
River Ambulance Dispatch & Handoff Board
Build-ready PRD for Antigravity
Prepared for JALAKAM HARIKRISHNA  |  Challenge deadline: 18 September 2026, 12:33 PM IST
Product goal: replace emergency dispatch and shift-handoff group chats with a fast, mobile-first board that makes every request, claim, completion, fuel level, and oxygen count visible and auditable.
1. Executive Summary
Small river islands operate five boat ambulances. Emergency requests and shift changes are currently coordinated through unstructured group chats, making it easy to miss urgent cases, lose fuel/oxygen information, and create duplicate work. The proposed web app is a lightweight dispatch and operational status board designed for clinic workers and boat captains on low-bandwidth mobile connections.
The MVP should prioritize speed over feature breadth: a clinic worker creates a request in under 30 seconds; captains see open requests immediately, claim a job with conflict protection, and mark it completed; every boat displays current availability plus fuel and oxygen; and past dispatches can be filtered by island.

4. MVP Scope
In scope
Five predefined boats with persistent IDs and display names (Boat 1 through Boat 5).
Emergency request creation with pickup island/location, urgency, patient condition, requester name/contact label, and timestamp.
Open-request queue with urgency-first ordering and request age.
Captain job claiming with atomic conflict protection.
Job lifecycle: Open -> Claimed -> In Transit -> Completed. (Allow Open -> Cancelled for incorrect requests.)
Boat status board showing Available, Assigned, In Transit, Maintenance/Unavailable, plus fuel % and oxygen tank count.
Shift handoff form per boat with fuel percentage, oxygen tanks available, notes, and handoff timestamp.
Dispatch history with island filter and date/time information.
Basic offline/error states and retry messaging for weak connectivity.
Public deployment using a free hosting/database option.
Out of scope for MVP
GPS tracking or live vessel location.
Payments, billing, or insurance workflows.
Complex identity management, SSO, password reset, or role administration.
Automated medical triage or clinical decision support.
Push/SMS/WhatsApp notifications requiring paid services.
Hardware integration for fuel or oxygen sensors.
5. Core User Flows
Flow A - Create emergency request
Health worker opens Dispatch screen.
Taps “New Emergency Request”.
Selects pickup island/location.
Selects urgency: Critical / High / Routine.
Selects patient condition: Critical, Serious, Stable, Unknown.
Optionally adds short notes.
Submits request.
System creates request with status Open and current timestamp, then returns a prominent success state with request ID and queue position.
Flow B - Captain claims and completes a job
Captain opens “Open Requests”.
Sees requests sorted by urgency and age.
Opens a request and taps “Claim Job”.
Server rechecks current request status before assigning captain/boat.
If still Open, request becomes Claimed and selected boat becomes Assigned.
Captain can mark In Transit when departing.
After handoff at destination, captain taps “Complete”.
System records completion timestamp and returns boat to Available.
Flow C - Shift handoff
Captain/shift lead opens boat card.
Taps “Handoff”.
Enters fuel % and oxygen tank count; optionally adds note.
Submits.
System records an append-only handoff record and updates the boat’s current operational snapshot.
The board shows the latest handoff timestamp so the next shift can verify freshness.

9. State Machines & Business Rules
Dispatch request states
OPEN -> CLAIMED -> IN_TRANSIT -> COMPLETED
OPEN -> CANCELLED
Optional recovery path: CLAIMED -> OPEN only through an explicit “Release job” action by the same captain or operations role; this is safer than silently reassigning.
Boat status rules
AVAILABLE: can be assigned. ASSIGNED: reserved for a claimed request. IN_TRANSIT: currently transporting a patient. MAINTENANCE: cannot be assigned.
When a request is completed, the assigned boat returns to AVAILABLE unless the captain explicitly flags it for MAINTENANCE during completion/handoff.
10. Edge Cases & Concurrency
Edge case
Expected behavior
Two captains claim simultaneously
Backend uses a conditional update/transaction: UPDATE request WHERE id=? AND status=OPEN. Exactly one request changes to CLAIMED; the other receives a conflict response.
Two captains try to use the last available boat
Boat assignment must also be atomic. One captain wins the boat reservation; the other sees “No available boat” and returns to the queue.
Captain closes browser after claiming
Request remains CLAIMED. The open queue does not duplicate the job. An optional timeout/release mechanism can be added later.
Weak or lost network during submit
Disable duplicate submission while pending; retry safely using a client-generated request UUID/idempotency key.
Boat has 0% fuel
Allow the record, but mark boat as “Not dispatch-ready” and block assignment if the product rule requires minimum fuel.
Oxygen count becomes 0
Allow the handoff record but surface a strong warning. MVP may block dispatch for critical cases based on configurable safety policy.
Stale handoff
Show “Handoff stale” badge with timestamp; do not hide the boat.
Incorrect request created
Permit dispatcher/operations to cancel with reason. Preserve audit event.
Refresh while a job is being claimed
Server is source of truth; client re-fetches authoritative status after mutation.
History has many records
Use pagination or cursor-based loading; default to recent records only.
Five boats unavailable
Board should still load, clearly showing zero available boats and all reasons.
Different shifts use same device
Do not depend on persistent personal login; require an easy display-name selector before actions or use a temporary session name.
11. Real-Time Strategy
MVP recommendation: use lightweight polling (for example every 5-10 seconds while the board is open) rather than a third-party real-time service. Polling is simpler, free, and more resilient for a prototype. Mutations should trigger an immediate re-fetch, so dispatch actions feel real-time without requiring sockets.
Future option: replace polling with WebSockets/SSE once the core workflow is stable and real operational scale justifies it.
12. Low-Bandwidth & Mobile Requirements
Responsive mobile-first layout; design primarily for 360-430 px wide screens.
No background video, large images, map tiles, or unnecessary animation.
Prefer system fonts and inline SVG/iconography over heavy icon libraries.
Keep the initial bundle small; lazy-load history/detail views where practical.
Use compact JSON payloads and fetch only the fields needed for board cards.
Use skeleton/loading states but keep the screen useful while data loads.
Provide explicit offline/error banners rather than silently showing stale information.
Primary CTAs must be thumb-friendly and at least roughly 44 px touch height.
Use high-contrast status chips that do not rely on color alone; include text labels.

15. Technology Recommendation for Antigravity
Choose the simplest free stack that Antigravity can scaffold and deploy quickly. A practical default is: React + Vite for the frontend, a small Node/Express API, and a free hosted PostgreSQL-compatible database or lightweight hosted backend. Use standard REST endpoints and polling for live updates. Avoid external paid APIs and avoid unnecessary infrastructure.
For the challenge prototype, a single repository and a single deployment target are preferred. Seed five boats and several demo islands/requests so the reviewer can immediately understand the workflow.

18. Trade-Offs to Document in Submission
Polling instead of WebSockets: simpler, cheaper, and sufficient for the scale of five boats, at the cost of a few seconds of update latency.
Lightweight role selection instead of authentication: dramatically reduces friction, but is not sufficient for production-grade accountability. Production should add authenticated identities and permissions.
No GPS map: keeps the app fast and free; pickup is represented as an island/location field in the MVP.
Append-only handoffs: improves auditability while keeping the current boat snapshot fast to read.
Backend-enforced claim locking: slightly more implementation work, but necessary to prevent duplicate dispatch under concurrency.
Five fixed boats in MVP: matches the challenge and simplifies the board; production can support dynamic fleet configuration later.
